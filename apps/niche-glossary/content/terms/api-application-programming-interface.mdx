# API (Application Programming Interface)

An **API (Application Programming Interface)** is a set of rules, protocols, and tools that allows different software applications to communicate with each other. APIs define the methods and data formats that applications can use to request and exchange information, enabling developers to integrate external services and functionality into their own applications without needing to understand the underlying implementation details.

## Core Concept

Think of an API as a waiter in a restaurant: you (the client application) tell the waiter (the API) what you want from the menu (available endpoints), the waiter takes your order to the kitchen (the server), and then brings back your food (the response data). You don't need to know how the kitchen prepares the food—you just need to know how to communicate your order correctly.

## How APIs Work

**Basic API workflow:**

1. **Client makes a request:** Application sends a request to the API endpoint with specific parameters
2. **API processes request:** The API receives and validates the request, then forwards it to the appropriate service
3. **Server responds:** The backend system processes the request and generates a response
4. **API returns data:** The API formats and returns the response to the client application
5. **Client uses data:** The requesting application receives and processes the returned data

## Types of APIs

### REST APIs (Representational State Transfer)

**Most common type** of web API:

- Uses standard HTTP methods (GET, POST, PUT, DELETE)
- Stateless communication
- Resources identified by URLs
- Returns data typically in JSON or XML format
- Example: `GET https://api.example.com/users/123`

**Advantages:**
- Simple and widely understood
- Scalable and performant
- Platform-independent
- Easy to cache

### GraphQL APIs

**Modern alternative to REST:**

- Allows clients to request exactly the data they need
- Single endpoint for all queries
- Reduces over-fetching and under-fetching
- Strongly typed schema
- Example: Query for specific user fields only

**Advantages:**
- More efficient data transfer
- Fewer API calls needed
- Self-documenting through schema
- Better for complex data requirements

### SOAP APIs (Simple Object Access Protocol)

**Enterprise-grade protocol:**

- XML-based messaging protocol
- Strict standards and contracts
- Built-in error handling
- More complex than REST
- Common in enterprise and financial systems

**Advantages:**
- High security standards
- ACID compliance support
- Built-in retry logic
- Language and platform independent

### WebSocket APIs

**Real-time, bidirectional communication:**

- Persistent connection between client and server
- Enables real-time updates
- Used for chat applications, live feeds, gaming
- Lower latency than HTTP polling

### Webhook APIs

**Event-driven communication:**

- Server pushes data to client when events occur
- No need for client to poll for updates
- Used for notifications and real-time updates
- Example: Payment confirmation notifications

## Common API Use Cases

**Third-party integrations:**
- Payment processing (Stripe, PayPal APIs)
- Social media posting (Twitter, Facebook APIs)
- Mapping and location services (Google Maps API)
- Communication (Twilio SMS API, SendGrid Email API)

**Internal microservices:**
- Different services within same organization communicate via APIs
- Enables modular, scalable architecture
- Each service has specific responsibility

**Mobile applications:**
- Mobile apps use APIs to communicate with backend servers
- Retrieve and update data from databases
- Authenticate users and manage sessions

**Data aggregation:**
- Pulling data from multiple sources
- Combining weather, news, stock prices, etc.
- Creating unified dashboards and reports

## API Request Components

### Endpoint/URL

The specific address where the API can be accessed:
```
https://api.example.com/v1/users
```

### HTTP Method

The action to be performed:
- **GET:** Retrieve data
- **POST:** Create new data
- **PUT/PATCH:** Update existing data
- **DELETE:** Remove data

### Headers

Metadata about the request:
```
Content-Type: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

### Parameters

Data sent with the request:

**Query parameters:** In the URL
```
https://api.example.com/users?page=2&limit=20
```

**Body parameters:** In request body (POST/PUT)
```json
{
  "name": "John Doe",
  "email": "john@example.com"
}
```

### Authentication

Verifying identity of the requester:
- API keys
- OAuth tokens
- JWT (JSON Web Tokens)
- Basic authentication

## API Response

### Status Codes

Indicate the result of the request:

- **200 OK:** Request succeeded
- **201 Created:** New resource created
- **400 Bad Request:** Invalid request
- **401 Unauthorized:** Authentication required
- **404 Not Found:** Resource doesn't exist
- **500 Internal Server Error:** Server-side error

### Response Body

Data returned by the API, typically in JSON:
```json
{
  "id": 123,
  "name": "John Doe",
  "email": "john@example.com",
  "created_at": "2024-01-20T10:30:00Z"
}
```

## API Documentation

Good API documentation includes:

- **Endpoints:** All available API endpoints
- **Methods:** Which HTTP methods are supported
- **Parameters:** Required and optional parameters
- **Authentication:** How to authenticate requests
- **Examples:** Sample requests and responses
- **Error codes:** Possible errors and meanings
- **Rate limits:** Request limitations
- **Versioning:** API version information

**Popular documentation tools:**
- Swagger/OpenAPI
- Postman
- API Blueprint
- ReadMe

## API Security

**Best practices:**

- **Use HTTPS:** Encrypt all API communications
- **Authentication:** Require proper authentication
- **Authorization:** Verify permissions for each request
- **Rate limiting:** Prevent abuse and overuse
- **Input validation:** Validate all incoming data
- **API keys:** Issue unique keys per client
- **Token expiration:** Use short-lived access tokens
- **CORS policies:** Control which domains can access API

## API Versioning

Managing changes over time:

**URL versioning:**
```
https://api.example.com/v1/users
https://api.example.com/v2/users
```

**Header versioning:**
```
Accept: application/vnd.example.v2+json
```

**Why version?**
- Maintain backward compatibility
- Allow gradual migration
- Support multiple client versions
- Deprecate old features safely

## API Rate Limiting

**Controlling API usage:**

- Limits number of requests per time period
- Prevents abuse and ensures fair usage
- Protects server resources

**Common limits:**
- 1,000 requests per hour
- 100 requests per minute
- Different tiers for free vs. paid users

**Response headers indicate limits:**
```
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 987
X-RateLimit-Reset: 1609459200
```

## Public vs. Private APIs

**Public APIs (Open APIs):**
- Available to external developers
- Often require registration for API key
- May have free and paid tiers
- Examples: Twitter API, Google Maps API

**Private APIs (Internal APIs):**
- Used within organization only
- Not exposed to public
- Facilitate internal service communication
- More control over who can access

**Partner APIs:**
- Shared with specific business partners
- Controlled access with agreements
- More features than public APIs
- Examples: B2B integrations
